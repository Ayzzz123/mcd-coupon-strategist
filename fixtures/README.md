# fixtures/ —— 录制的真实 MCP 响应

这里的 JSON **全部来自对麦当劳官方 MCP Server 的真实调用**，用于让 `demo.py`
在没有 Token、不联网的情况下也能跑通完整链路。

| 文件 | 来源工具 | 说明 |
|---|---|---|
| `menu.json` | `query-meals` | 真实响应的**节选**：完整菜单有 100+ 项，只保留 demo 用到的 4 项，字段与取值未改动 |
| `coupons.json` | `query-store-coupons` | **逐字保留**，未做改动（当天该门店返回 2 张券） |
| `orders.json` | `order-list` | **逐字保留**，未做改动（10 条历史订单） |
| `prices.json` | `calculate-price` | **逐字保留**的计价响应，按商品组合签名索引 |
| `coupon_probe.json` | `calculate-price`（带券计价） | **逐字保留**。用券自带的 `productCode` + `couponId` 调价，`discount` 即券的**精确价值** |
| `available_coupons.json` | `available-coupons` | ⚠️ **该工具返回的是 Markdown 文本，不是 JSON**。文本原样放在 `raw` 字段里，解析器见 `parse_available_coupons()` |

## 采集信息

- **时间**：2026-10-12 21:59 ~ 22:00（`available_coupons.json` 为 2026-10-13 22:18）
- **门店**：麦当劳南京东城汇餐厅 `storeCode=1990622`
- **下单方式**：到店自取 `orderType=1 beType=1`
- **`available-coupons` 例外**：该工具**不接受任何参数**，返回账户全域的麦麦省券，
  不限于某个门店 —— 所以它单独录了一份

## 为什么要有「录制」

`demo.py` 的定位是**零配置可复现**：访客 clone 下来敲一条命令就能看到真实输出，
不需要先申请 Token、配置连接器。

业务逻辑一字未改 —— 真实运行时，这些响应由 Skill 编排层通过 MCP 实时获取。
本目录只是把「实时」换成「录播」。因此 `demo.py` 同时也是这套数据流水线的
端到端回归测试。

## 计价组合签名

`prices.json` 的 key 是商品组合的规范签名：**按商品编码升序，拼成 `code:qty`**，
用 `+` 连接。例如：

```
1440:1+4810:1+9900008751:1     →  汉堡 + 薯条 + 可乐  →  4650 分（46.5 元）
```

⚠️ 响应里所有金额字段单位都是**分**。`3350` 表示 33.5 元。
这与 `orders.json` 里 `realTotalAmount` 的**元**（如 `"36.5"`）方向相反 ——
这是本项目最容易混淆的一处单位差异。

## 如何补充新的录制

```
1. 用真实 MCP 调用 calculate-price，参数 items=[{productCode, quantity}]
2. 把完整响应（含 data.price 等字段）追加到 prices.json 的 prices 映射下
3. key 用上面说的签名规则
```

**不要手工估算价格填进来** —— 这与项目「绝不猜测价格」的铁律冲突。
`demo.py` 遇到未录制的组合会直接报错，而不是猜一个值。

如果 MCP 的菜单或券发生变化导致 demo 报错，重新录制对应响应即可，
不需要改 `demo.py`。

## 为什么要单独录一份「带券计价」

券的真实价值有两条获取途径，**带券计价比菜单反查精确**：

| 券 | 菜单反查 | 带券计价 |
|---|---:|---:|
| 中薯条买一送一 | 14.5 元 | 14.5 元 |
| 王牌小食拼 | **0（价值未知）** | **6.6 元** |

「王牌小食拼」标题里没有数字，反查识别不出券型只能返回 0；
带券计价能拿到真实的 6.6 元。所以 `coupon_probe.json` 是必需的 ——
**没有它，这张券在报告里会被显示成「价值未知」，而它其实值 6.6 元。**

调价时必须用**券自带的商品码**（`coupons.json` 里的 `products[].productCode`），
不是菜单商品码 —— 用错会返回 `600012 促销规则不支持该商品`。

## `orders.json` 里有两类「不是普通消费」的订单

这份订单是真实录制的，里面正好包含三种状态 —— 也正是消费画像口径的验证素材：

| 订单状态 | 笔数 | 怎么处理 |
|---|---:|---|
| 订单已完成 | 6 | 正常计入 |
| **部分退款** | 2 | 保留但如实提示「支出可能略偏高」—— 接口不给退款金额，**不猜** |
| **整单退款** | 1 | 直接过滤 |
| 0 元订单 | 2 | 不计入客单价，但算一次点单机会 |

因为这份数据里同时有 2 笔 **0 元订单**和 2 笔 **部分退款**，
口径处理是否正确会直接体现在 demo 输出上 —— 客单价是按 6 笔有支出的订单算出的
**17.25 元**，而不是按 8 单摊薄的 12.94 元。这个差别会一路传导到券包体检与用券排程的结论。

## 为什么「可领取的券」在 demo 里全是「价值未知」

这不是解析失败，是**数据事实**。三张可领取券的价值都只能靠菜单反查
（该工具不返回 `couponId`，所以「带券计价实测」这条路走不通），而：

| 可领取的券 | 券面商品名 | 这份菜单快照里有吗 |
|---|---|---|
| 免费脆薯饼 | 脆薯饼 | ✗ |
| 人气麦旋风买一送一 | 麦旋风 | ✗（只有「经典麦旋风」等，名称无法安全对应） |
| 9.9元中杯冰美式 | 中杯冰美式 | ✗（只有「麦咖啡™美式」，不是同一个名字） |

菜单快照采集于 **21:59**，而脆薯饼、冰美式这类商品并不在该时段的菜单里 ——
所以「查不到」是当时的真实情况。

**我们没有为了让 demo 好看而往菜单里塞一个能匹配上的商品名。**
「宁可少报，不可编造」在「拿不到数据」时才是真正的考验。
能力本身由 `src/test_claimable.py` 用真实的 10-10 菜单价覆盖验证
（那一版菜单里有「脆薯饼 8.0 元」，免费券因此能算出 8.0 元）。
