基于麦当劳中国 MCP 打造的点餐成本助手，做两件事：

**短期 —— 这一单怎么点最省**
- 拉取**当前门店**的实时菜单与价格
- 拉取你**账户里当前门店可用**的优惠券
- 枚举「单品 / 套餐 / 券组合 / 加购凑单」的候选方案
- 用 MCP 的 `calculate-price` 逐方案**真实计价**（而不是猜）
- 输出最省钱的方案，以及**为什么不推荐更便宜但吃不饱的选项**

**长期 —— 你白扔了多少钱**
- **券的沉默成本**：你手里有几张券即将过期？那就是正在流失的钱
- **消费习惯画像**：近 N 个月花了多少、客单价是否偏高、哪些单品该改成套餐
- 数据来自 `order-list` 历史订单 + `query-my-coupons` 券存量

## 快速体验（30 秒）

```bash
git clone https://github.com/Ayzzz123/mcd-coupon-strategist.git
cd mcd-coupon-strategist
python demo.py
```

**零第三方依赖**（只用标准库）、**不需要 MCP Token**、**不联网**。
`demo.py` 读取 `fixtures/` 里录制的真实 MCP 响应，跑通两条链路：

```
链路 A · 单次省钱
门店：麦当劳南京东城汇餐厅(1990622)（到店自取）
需求：想吃「汉堡 + 薯条 + 可乐」，预算 40 元

推荐方案
  组合：套餐：麦辣鸡腿汉堡三件套
  实付 33.5 元

  · 单点：麦辣鸡腿汉堡 + 中薯条 + 可乐 —— 实付 46.5 元

  → 同样吃到「汉堡 + 薯条 + 可乐」：33.5 元 vs 46.5 元，差 13.0 元。

链路 B · 消费审计
【一】券的沉默成本
  你有 2 张将在 4 天内陆续过期（面值 21.1 元）。
    · 中薯条买一送一  省 14.5 元  还剩 4 天

  · 中薯条买一送一    需额外消费 0.56 元，净赚 13.94 元    还剩 4 天
  · 王牌小食拼    需额外消费 2.96 元，净赚 3.64 元    还剩 4 天

用券排程
  窗口 4 天（券全部过期前） · 点单频率 0.089 单/天
  → 这期间你大概只会点 1 单，最多用掉 1 张券
    第 1 单 → 中薯条买一送一    净赚 13.94 元
  排不上（1 张 · 可实现 ¥3.64）
    · 王牌小食拼    净价值 3.64 元    还剩 4 天
  券包可实现 ¥17.58，但机会只够用掉 ¥13.94 —— 剩下 ¥3.64 注定随券过期浪费。

  麦麦省共 7 条券记录：已领取 4 条、可领取 3 条（同名去重后）

可领取的券
  你还有 3 张券没领（领取免费）

【无法判断】3 张

  另外别忘了机会有限：上面排程算出，窗口内的点单机会已被你手里的券占满 ——
```

## 一个真实例子

同一个账号，同一个门店，两种问法：

**问「今天怎么点最省」** →

```
推荐方案
  组合：套餐：麦辣鸡腿汉堡三件套
  实付 33.5 元
备选方案
  · 单点：麦辣鸡腿汉堡 + 中薯条 + 可乐 —— 实付 46.5 元
```

> 同样吃到「汉堡 + 薯条 + 可乐」：套餐 33.5 元，单点 46.5 元，**差 13 元**。

**问「我最近在麦当劳花了多少」** →

```
【一】券的沉默成本
  你有 2 张将在 4 天内陆续过期（面值 21.1 元）。
  优先处理这几张：
    · 中薯条买一送一  省 14.5 元  还剩 4 天
    · 王牌小食拼  省 6.6 元  还剩 4 天

【二】消费习惯
  订单数：8 单      总支出：103.5 元      客单价：12.94 元
  洞察：
    · 近 3 个月你在麦当劳共消费 103.5 元，平均每单 12.94 元。
```

> **本月最该做的事：先把 21.1 元的券用掉，这笔钱不用就是纯损失。**

第二个问题的价值不在这一次的数字大小，而在于**它是持续性的**：
第一个问题每单只影响一次；第二个问题每次都会告诉你又有什么在悄悄过期 ——
**而这是一次性工具永远给不出的答案。**

注意「王牌小食拼」那个 6.6 元：这张券的标题里没有数字，菜单里也没有对应商品，
**靠反查原价这条路根本走不通**。它的价值是把券的商品码传给 `calculate-price`
**实测**出来的 —— 而不是估一个「差不多」的数。

> 这两段输出与 `python demo.py` 的结果**逐字一致** —— 你可以自己跑一遍验证。

## 我们做对了什么别人没做的

省钱类工具已经很多了，多到这次比赛报名里就有好几支在做同一件事。所以先说清楚**我们的不同点到底在哪**：

| 常见做法 | 我们的做法 | 差别 |
|---|---|---|
| 让模型估算价格 | 所有金额由 MCP `calculate-price` 回填 | 模型给不出真实价格，只能猜 |
| 只说「推荐买这个」 | 说清**省在哪**：哪张券、哪个套餐、加了什么 | 用户才能学会，而不是依赖工具 |
| 为用券鼓励凑单 | 主动检测**凑单陷阱**并劝退 | 凑单常常反而更贵 |
| 只看这一单 | 同时看**历史订单 + 券存量** | 一次性工具看不到长期结构 |
| 券是「可用资源」 | 券是**有保质期的钱** | 过期即损失，这是本项目独有的视角 |
| —— | **券的沉默成本** | 别处见不到这个指标 |

<div align="center">

> **差异化内核：别处都在帮用户花钱，我们在帮用户止损。**
> 下单前省的那几块钱是「收益」，快过期的券是「损失」——
> 人对损失的敏感度是对收益的两倍，而这个数字从来没人给他算过。

</div>

### 关键实现：怎么知道一张券真值多少钱

「券的沉默成本」要成立，前提是得知道**每张券真实值多少钱**。而 MCP 返回的券通常只有名字，没有面值：

```
「中薯条买一送一」  →  值多少钱？
「9.9元中杯冰美式」 →  值多少钱？
「王牌小食拼」      →  值多少钱？
```

**首选：直接问收银台。** 把券自带的商品码连同 `couponId` 传给 `calculate-price`，
返回的 `discount` 就是这张券的**精确价值**，`price` 就是用券实付：

| 券 | 实测结果 |
|---|---:|
| 中薯条买一送一 | 14.5 元 |
| 王牌小食拼 | **6.6 元** |

**兜底：从菜单反查原价**（拿不到券的商品码时用）：

| 券形态 | 价值推算 | 本例结果 |
|---|---|---|
| 满减券 `满50减12` | 直接取减免额 | 12.0 元 |
| 买一送一 `中薯条买一送一` | 取该商品菜单单价 | 14.5 元 |
| 免费券 `免费脆薯饼` | 取该商品菜单单价（券面即免费） | 脆薯饼单价 |
| 固定价券 `9.9元中杯冰美式` | 菜单原价 − 固定价 | 23.0 − 9.9 = 13.1 元 |

**为什么首选实测**：「王牌小食拼」标题里没有数字、菜单里也没有对应商品 ——
反查只能返回 0（价值未知），而它实际值 6.6 元。
反查不只是可能低估，**还会把真实存在的价值报成 0**。

**两条路都走不通时，一律取 0 并在报告中标注「价值未知」**，
绝不估一个「看起来合理」的数。宁可少报，不可编造。

### 更进一步：券包体检

知道「你正在白扔多少钱」之后，下一个问题自然是：**这笔钱该怎么不白扔？**

答案取决于一个反直觉的事实 —— **券的名义面值，从来不是它对你的真实价值**：

```
净价值 = 券面价值 − 为用这张券、你本来不会花的那部分钱
```

一张「满50减12」的券，如果客单价是 13 元 —— 为了用它得点到 50 元，
**名义省 12，实际多花 37，净亏 25**。

按这个公式，券包会被切成四类：

| 类别 | 判定条件 | 建议 |
|---|---|---|
| **顺手可用** | 你本来就会花到门槛 | 直接用，净价值 = 券面价值 |
| **努一把** | 差额 < 券面价值 | 凑单后仍净赚，标出净赚多少 |
| **纸面富贵** | 差额 ≥ 券面价值 | **明确劝退**，算出硬用会亏多少 |
| **无法判断** | 券面反查不到原价 | 如实标注，不估算 |

最后汇总成一句可以直接行动的话：

> 券包名义 ¥150 → 按你的消费习惯只拿得到 ¥60。

**第三类是全篇最反直觉的地方** —— 别的工具都在说「你有券，快去用」，
我们说「这几张别用」。这与「别处帮用户花钱，我们帮用户止损」的立场一致。

> ⚠️ 判定用的「自然消费基准」取自历史订单的**客单价**，是一个保守近似、
> 而非精确值。这个假设写在报告里，不藏在代码里。

### 再进一步：用券排程

「可实现 ¥60」有个隐含前提 —— **这些券你都有机会用掉**。
但券会过期，而你点单的次数有限。

于是有了第二层：先推算「券全部过期前你还会点几单」，再在这个约束下分配券。

```
窗口 20 天 · 点单频率 0.09 单/天
→ 这期间你大概只会点 1 单，最多用掉 1 张券

建议安排
  第 1 单 → 满20减12    净赚 5.0 元

排不上（1 张 · 可实现 ¥5.0）
  · 免费脆薯饼    净价值 5.0 元    还剩 20 天

券包可实现 ¥10.0，但机会只够用掉 ¥5.0 —— 剩下 ¥5.0 注定随券过期浪费。
```

**「可实现的券，未必用得上」** —— 这是比「券面价值加总」更硬的一层。
大多数省钱工具连第一层都没做，这一层基本没人碰。

> 三个假设都写在代码注释里，不藏着：你在窗口内本来就会点 K 单、
> 每单最多用 1 张券、用券不改变你的点单次数。

### 最后一层：还没领的券

前面三步看的都是**你已经领到手的券**。但你的券源不止这些 ——
`available-coupons` 会同时返回「已领取」和**还没领**的券：

```
麦麦省共 7 条券记录：已领取 4 条、可领取 3 条
可领取：免费脆薯饼 / 人气麦旋风买一送一 / 9.9元中杯冰美式
```

**别的工具都在帮你「用」券，没人提醒你「还有券没领」。**
未领取的券是唯一一种零成本的省钱来源，所以我们把它也做进了体检 ——
沿用同一套净价值框架，但问的是不同的问题：

| 券包体检问 | 可领取券问 | 类别文案 |
|---|---|---|
| 这张券该不该**用** | 这张券该不该**领** | 领了就能用 / 领了要凑一点 / **领了也用不上** |

「领了也用不上」是这里最反直觉的一类：领券本身免费，
但你**为了用它而消费**不是 —— 这跟券包体检是同一套标准。

还有一处必须诚实的地方：**这批券拿不到 `couponId`**（工具不返回），
所以上一节那套「带券计价实测」走不通，只能靠菜单反查；
反查不到时如实标「价值未知」，**不猜**。如上面 demo 输出的 3 张全是未知 ——
原因是那份菜单快照采集于 21:59，脆薯饼与冰美式并不在该时段的菜单里。

> ⚠️ **不擅自替用户领券。** 领取（`auto-bind-coupons`）会改动账号状态，
> 必须先取得用户明确同意。工具负责把「有哪些没领、值不值」摆清楚，
> 领不领由用户决定。

> 另外，这批券**没有有效期**，所以它们不进用券排程（排程的窗口天数是靠有效期算的）。
> 渲染时也刻意不输出剩余天数 —— 把「未知」说成「无期限」就是编造。

## 目标用户

- **学生党 / 打工人**：预算固定，希望同样吃饱的前提下花得更少
- **持券用户**：手里攒了一堆券，但不知道哪张快过期、哪张该用
- **选择困难用户**：不想在菜单里反复横跳，希望直接得到一个明确答案
- **想知道自己花了多少钱的人**：从没算过在麦当劳的月度开销

## 快速开始

### 1. 申请麦当劳 MCP Token

前往麦当劳 MCP 开放平台 <https://open.mcd.cn/mcp> ，使用手机号登录后在控制台激活并复制 MCP Token。

### 2. 配置 MCP 连接

本项目提供脱敏示例配置 [`mcp-config.example.json`](./mcp-config.example.json)：

```json
{
  "mcpServers": {
    "mcd-mcp": {
      "type": "streamablehttp",
      "url": "https://mcp.mcd.cn",
      "headers": {
        "Authorization": "Bearer ${MCD_MCP_TOKEN}"
      }
    }
  }
}
```

将 `${MCD_MCP_TOKEN}` 替换为你自己的 Token 后，写入 MCP Client 的配置。**请勿将真实 Token 提交到任何公开仓库。**

### 3. 在 WorkBuddy 中启用

1. 打开 WorkBuddy，左侧边栏进入【专家 · 技能 · 连接器】→【连接器】页签
2. 点击右上角【自定义连接器】→【配置 MCP】
3. 粘贴上面的 JSON（替换 Token），点击【保存】
4. 回到【自定义连接器】，将 `mcd-mcp` 设为【启用】

### 4. 开始使用

直接对话即可，例如：

```
我在麦当劳点外卖，门店选好之后帮我算一下：
```

## 使用示例

**示例一：预算内吃饱**

> **你**：预算 35 元，想吃鸡类主食 + 一个配餐，帮我选。
>
> **助手**：已查询当前门店菜单与你名下可用券，为你计价了 3 个候选方案：
>
> | 方案 | 组合 | 实付 |
> |---|---|---|
> | ✅ 推荐 | 麦辣鸡腿堡三件套（汉堡 + 中薯条 + 可乐） | **33.5** |
> | 备选 | 单点：麦辣鸡腿堡 + 中薯条 | 37.0 |
> | 不推荐 | 单点：麦辣鸡腿堡 + 中薯条 + 可乐 | 46.5 |
>
> 推荐三件套：**33.5 元拿到三样**，比只买两样的单点组合还便宜 3.5 元，
> 比同内容的单点组合省 13 元。这是套餐结构本身带来的价差，不必再叠加优惠券。

**示例二：凑单陷阱提醒**

> **你**：我有一张「满 50 减 12」的券，是不是该凑单？
>
> **助手**：不建议。你当前想买的商品合计 46.5 元，为触发门槛需要再加 3.5 元商品，
> 实付变为 46.5 + 3.5 - 12 = 38 元；而直接买三件套只要 33.5 元。
> 也就是说，**凑单用券后反而比直接买套餐贵 4.5 元**。
> 除非你本来就想吃那个凑单品，否则不划算。

> 这是一个**演示场景**（该账户当前没有满减券），用于说明凑单陷阱的判定逻辑。
> 逻辑本身由 [`src/test_saver.py`](./src/test_saver.py) 覆盖。

> 以上金额均来自 MCP `calculate-price` 的真实返回，非估算值。

## 架构

<img src="./assets/architecture.svg?v=2" alt="架构图：MCP 数据底座 → 适配层 → 链路 A 单次省钱 / 链路 B 消费审计" width="100%">

两条链路**共用同一套 MCP 数据底座**，但回答的是完全不同的问题：

- **链路 A（短期）**：`saver.py` —— 枚举候选组合，每个组合都交给 `calculate-price` 真实计价，输出这一单的最省方案
- **链路 B（长期）**：`auditor.py` —— 读 `order-list` 历史订单与 `query-my-coupons` 券存量，输出结构性浪费报告

衔接两者的是 `mcd_adapter.py`：它负责**唯一一次**的「分 → 元」换算、字段映射、退款过滤，以及券面价值反查。算法层不接触原始响应，因此不会出现单位错乱的幻觉。

## 设计原则
1. **绝不猜测价格** —— 所有金额均来自 MCP `calculate-price` 的返回结果。
2. **宁可少报，不可编造** —— 券的价值若无法从菜单反查到原价，取 0 并在报告中标注，而不是估一个看起来合理的数。
3. **省在哪要说清** —— 每个推荐都附带省钱归因，而不是只给一个数字。
4. **不诱导消费** —— 为用券而凑单如果导致实付上升，必须明确提示。
5. **退款不算消费** —— 历史订单中的整单退款会被过滤，避免月度支出虚高。
6. **信息以官方为准** —— 价格、供应状态、券的可用范围均以麦当劳官方渠道实时结果为准。
7. **不擅自改动账号状态** —— 领券（`auto-bind-coupons`）属写操作，必须先取得用户明确同意；
   工具负责把选项摆清楚，决定权留给用户。
8. **不知道就说不知道** —— 未领取的券拿不到有效期，就不输出剩余天数；
   数据缺失时如实说缺失，不用「无期限」这类说法掩盖。
